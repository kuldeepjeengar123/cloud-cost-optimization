Cloud Cost Insights: End-to-End Flow

AWS cost data comes in from the Cost Explorer API only and is cleaned into one shape. An LLM pipeline normalises it and loads context, and parallel agents turn it into charts, KPIs, anomalies, forecasts and recommendations. The delivery layer writes the report, and a person from the RE team must approve every recommendation before anything changes in AWS. The same approval gate is reachable by AI agents through the MCP server, as shown in the MCP workflow section.

End-to-end flow

Each band is one layer of the code. Steps 1 to 5 follow the reference architecture. Dashed green lines show where human decisions are recorded and where they can be undone.

Data flow Runs in parallel, no LLM Human decision recorded or undone

Orchestrator run graph

These are the steps and fan-outs as built in src/orchestrator.py, using the same step names that appear in the live progress stream. The three guardrail agents run on one thread pool. Charts and the four analysis agents run on a second pool. Only the summary waits for the analysis agents.

Two layers of anomaly detection

Step 2 flags spikes with a z-score check in code. The run_cost_anomaly agent then explains them. A spike is still reported if the LLM misses it or fails.

Agents never stop the run

Each agent catches its own errors and returns an empty result. The rest of the pipeline continues with whatever succeeded.

Model tiers

Each step has its own model setting. The usage report uses the cheap tier. The other agents use the capable tier.

Current build: every tier defaults to the same free model

LLM client

All LLM calls go through src/llm/client.py (OpenRouter). It retries short-lived errors and switches to a backup key on 401, 402, 403 or 429.

Write guard

Every AWS change passes one guard function. Without AWS_ALLOW_REAL_WRITES=1 the change is a dry run, and region and tag allowlists still apply when it is on.

Rollback

Each instance's state is saved before a batch is committed. Stop, resize and tag changes can be reversed. Terminate is marked as irreversible.

MCP server

AI agents can list, preview and approve recommendations through MCP tools. Approval tools check the RE-team token, and every call goes to an audit log with secrets removed.

LangGraph orchestrator

src/orchestrator_graph.py rebuilds the same flow as a LangGraph StateGraph, with a real fan-out for the three guardrail agents.

Current build: tested, not wired in · still uses a single Step 3.2 call

MCP workflow: agent to RE team

The MCP server (mcp_server.py, server name aws-cost-ops) is the one channel an AI agent has into the AWS state. Read tools are open to any caller. Every change follows the same two-stage gate as the dashboard: raise, then the RE team stages a decision on every open request, then one batch commit. There is no direct tool that calls AWS.

Data flow Alternative or recovery path Human decision recorded or undone

Request status lifecycle

Each recommendation moves through these states. The states are taken from the list_recommendations filter. The states dismissed and acknowledged are also valid filters and sit outside the approval path.

No shortcut to AWS

There is no standalone tool that calls AWS to make a change. Every change is a recommendation that goes through raise, stage and commit.

Batch gate

commit_approved_changes refuses to run while any request is still pending_re. The whole queue must be approved or declined first.

RE token

Stage, unstage, commit and rollback need re_token to match RE_TEAM_TOKEN. Read, raise and withdraw do not need it.

Current build: if RE_TEAM_TOKEN is unset, the gate is open (local demo mode)

Audit trail

Every call, allowed or denied, is appended to outputs/mcp_audit.jsonl. Approval steps also land in the decision log next to human dashboard actions.

Rollback

Stop, resize and tag changes from a committed batch can be undone by batch_id. Terminated instances and CSV-backend actions are reported as not reversible.

Demo order

One run followed from the Cost Explorer input to an approved change. AWS credentials with Cost Explorer access are needed. An OpenRouter API key is needed for the LLM steps.

  1. IN

    Start Postgres and Redis with docker compose up -d. Show the Cost Explorer response and explain how it is reshaped into four tables.

  2. M1

    Run python main.py --query "Which service drove the biggest cost spike?". Point out the validation, deduplication and normalization counts in the log.

  3. M2

    Show the Step 1 schema map, then the Step 2 correlations and anomaly signals. Show the three guardrail agents finishing in parallel.

  4. M3

    Show the five concurrent agents, then the summary that uses their results.

  5. M4

    Open outputs/insights_*.md for the executive view and the matching .json for charts, KPIs and lineage.

  6. M4

    Run python server.py and open http://127.0.0.1:8765. Run the pipeline and watch each step complete live.

  7. M4

    Raise a recommendation, stage it as the RE team, and commit the batch. Without AWS_ALLOW_REAL_WRITES=1 the commit is a dry run. Close on the write guard and rollback.

Step names, thresholds and model tiers are taken from the cloud-cost-optimization source, with src/orchestrator.py as the active orchestrator. Review before presenting.
